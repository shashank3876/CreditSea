## 4. Borrower Journey

Implement the entire borrower application flow.

### Step 1: Sign Up / Login

Create polished signup and login screens with validation, loading indicators, success messages, and useful error messages.

After login, redirect borrowers to their application portal and internal executives to their permitted dashboard.

### Step 2: Personal Details and Business Rule Engine (BRE)

Collect:

- Full name
- PAN
- Date of birth
- Monthly salary
- Employment mode: Salaried, Self-Employed, Unemployed

Validate all eligibility rules on the backend.

Rules:

- Age must be between 23 and 50 inclusive.
- Monthly salary must be at least ₹25,000.
- PAN must match the format `^[A-Z]{5}[0-9]{4}[A-Z]$`.
- Employment mode cannot be Unemployed.

Reject the application if any rule fails.

Return clear, field-specific error messages and display them on the frontend.

Calculate age correctly using the date of birth and the current date. Do not calculate age using a rough difference in years.

Client-side validation is allowed for user experience, but server-side validation is authoritative.

Do not claim the PAN is genuine merely because its format is valid.

Prevent users from bypassing eligibility checks by directly calling the API.

Persist the relevant eligibility outcome and validation errors where appropriate, without unnecessarily exposing sensitive PAN information.

### Step 3: Salary Slip Upload

Allow PDF, JPG, and PNG files only.

Requirements:

- Maximum file size: 5 MB.
- Validate extension, MIME type, and file signature where practical.
- Reject unsupported, oversized, or malformed uploads.
- Prevent path traversal and unsafe filenames.
- Associate the file with the correct borrower and loan application.
- Restrict file access to authorized users.
- Do not expose salary slips through unrestricted public URLs.

Use Replit-supported persistent storage or object storage when available. Do not assume files stored on a deployment's temporary filesystem will survive restarts or redeployments.

If persistent or private file storage requires an external service or credential, implement the storage abstraction, explain the missing dependency, and request only the required configuration.

### Step 4: Loan Configuration and Application

Provide two sliders:

- Loan amount: ₹50,000 to ₹5,00,000.
- Tenure: 30 to 365 days.
- Annual interest rate: fixed at 12%.

Display a live calculation panel.

Use the exact simple-interest formula:

SI = (P × R × T) / (365 × 100)

Where:
- P = principal amount in rupees.
- R = 12.
- T = tenure in days.

Total repayment = principal + interest.

Implement calculations using integer paise or another safe monetary representation. Apply a consistent rounding policy to interest and repayment totals, and use that same policy throughout the backend and frontend.

The frontend may preview the calculation, but the backend must recalculate and persist the authoritative values.

On clicking Apply:

- Verify the borrower is authenticated.
- Verify personal details and eligibility.
- Verify the salary slip is uploaded.
- Verify the loan amount and tenure.
- Create the loan with status `APPLIED`.
- Persist all required fields.
- Return the loan details.
- Prevent duplicate submissions caused by repeated clicks or retries.

Show an application confirmation and loan reference number.

Allow the borrower to view their application status and loan details.

## 5. Operations Dashboard

Create a professional internal dashboard with four modules:

1. Sales
2. Sanction
3. Disbursement
4. Collection

Each executive must see only their authorized module. Admin can access all modules.

### Sales Module

Purpose: Track registered borrowers who have not yet submitted loan applications.

Display useful lead information, registration date, borrower identity, and lead status.

Implement search, filtering, pagination, and appropriate empty states.

Sales users must not be able to approve, reject, disburse, or record payments.

### Sanction Module

Display loans in `APPLIED` status.

Show the borrower details, requested principal, tenure, interest, total repayment, application date, and securely accessible salary slip.

Provide:

- Approve loan.
- Reject loan with a mandatory rejection reason.

Transitions:

`APPLIED → SANCTIONED`

`APPLIED → REJECTED`

Validate the transition on the backend. Prevent repeat decisions and unauthorized status updates.

### Disbursement Module

Display only loans in `SANCTIONED` status.

Provide a confirmation action to mark the loan as disbursed.

Transition:

`SANCTIONED → DISBURSED`

Record the disbursed amount, disbursement timestamp, and executing employee.

Prevent disbursement of rejected, already disbursed, or otherwise ineligible loans.

### Collection Module

Display loans in `DISBURSED` status, including:

- Principal.
- Total repayment.
- Amount paid.
- Outstanding balance.
- Payment history.
- Borrower information.

Allow collection executives to record payments with:

- UTR number.
- Amount.
- Payment date.

Validation requirements:

- UTR must be unique across all payments.
- Normalize UTR values before checking uniqueness.
- Enforce uniqueness with a MongoDB unique index.
- Amount must be greater than zero.
- Reject payments that exceed the outstanding balance.
- Reject payments against loans that are not disbursed.
- Validate the payment date and all required fields.
- Record the employee who recorded the payment.
- Prevent race conditions and duplicate processing.

Outstanding balance:

`outstandingBalance = totalRepayment - totalPaid`

When the amount paid equals the total repayment, automatically transition:

`DISBURSED → CLOSED`

Use MongoDB transactions where supported to keep the payment record and loan totals consistent. Handle concurrent payment attempts and duplicate-key errors correctly.

Provide a detailed payment history with dates, UTR numbers, amounts, and recorded-by information.

Do not permit direct client-side modification of balances or statuses.
